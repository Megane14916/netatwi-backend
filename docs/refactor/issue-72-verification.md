# #72 退会済み・不存在ユーザーのセッション無効化

基準: `2413c2778ebed78055c7a1c17838ae08b43a5a64`。base: `fix/step-11-bugs`。

共通before_requestで署名済みsessionのuser_idをDBの有効Userと照合する。
不存在・退会済み・無効な型/範囲の場合はsession全体（管理者名・審査員資格を含む）を
clearしてから既存routeへ渡す。route固有の未ログイン401を維持し、
`/api/me`は200と`{"logged_in": false}`、公開GETは匿名表示になる。
新しい認証を必要とするAPIを増やさず、既存の認証入口すべてに適用する。

## 検証

Python 3.11.16、一時SQLite、通信拒否。23保護API × 退会済み/不存在と
別ブラウザ退会後の投稿拒否・me匿名化の47ケースを追加。
修正前の最初の43ケースはすべて失敗、修正後は47ケース成功。
拒否後のsession全消去と全テーブル件数の保持を確認した。
OAuth再ログインは既存のaccount_deleted拒否を維持する。

既存news管理fixtureの架空IDは実在Userへ変更して通常動作の検証を保持。
架空IDや退会済みviewerをログイン済みとして扱う特性テストだけを
新契約へ更新した。権限・期間・有効ユーザーの業務契約は変更していない。
全体pytest/CI/レビュー結果は個別PRに記録する。

## 影響・残件

セッション付きrequestにUserの読込が増える。ログイン形式とURLは維持し、
frontendの既存logged_in/401処理を使える。schema/migration/設定変更は不要。
再ログインで退会アカウントを復活させない。OAuthの既存拒否を引き継ぐ。
本PRのrevertで戻せるが古いsessionからの操作も再び可能になる。

やってないこと: ユーザー物理削除・匿名化、既存投稿削除、#18の権限共通化、
すでに実行中の別requestを中断する仕組み、構成整理。masterへはマージしない。
